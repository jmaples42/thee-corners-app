## What Corners is

Two-pillar Expo/React Native + Firebase app: **Share** (private group music sharing in "Corners") and **Browse** (curated weekly new-release picks with editorial commentary and user reviews).

## Current state (everything below is shipped, not planned)

- **Phone auth**: real Firebase `signInWithPhoneNumber`, session persisted via AsyncStorage until explicit sign-out. Real SMS delivery is confirmed working on real devices (Blaze billing + open US/CA region policy + Firebase App Check with App Attest, enforced). OTP entry auto-fills from the iOS "Code from Messages" QuickType suggestion (`textContentType="oneTimeCode"` on a single hidden input overlaying the 6 visual boxes — see `src/screens/AuthScreen.tsx`).
- **App Check**: dual-instance bridge — `@react-native-firebase/app-check` does the real App Attest handshake (native-only capability), and a `CustomProvider` in `src/firebase/appCheck.ts` forwards that token into the plain JS SDK's App Check instance, which is what `firebase/auth`'s `signInWithPhoneNumber` actually reads from. **App Attest never works in the iOS Simulator** — phone auth (real numbers and Firebase test numbers alike, once App Check enforcement is on) will fail there; test on a real device, or use a Firebase test phone number (Firebase Console → Authentication → Sign-in method → Phone → "Phone numbers for testing") knowing it'll still hit the same App Check wall in Simulator specifically.
- **Design system**: colors/fonts sourced from the live marketing site (corners-blush.vercel.app), applied via `src/theme/colors.ts` (values updated, old key names kept intentionally to avoid a large call-site rename — see task `task_3c591d43` if still open).
- **Navigation**: floating 2-tab pill bar in `src/navigation/AppNavigator.tsx`, hand-rolled (no react-navigation stack in use despite the dependency being present). **Connect** = your corners/chats + create a corner; **Discover** = new releases today, intended home for future curation products (playlist hub, artist-hosted corners). Profile and Settings are deliberately cut for now (`ProfileScreen`/`SettingsScreen` still exist but are unreachable), which means **there is currently no way to sign out in the UI**.
- **Browse**: full real content synced from the marketing site — masthead, all real releases with editorial copy, "Still in Rotation," "Still Trending — Best of 2026" (live from Firestore, see below), and a full methodology page (`src/screens/MethodologyScreen.tsx`).
- **Reviews**: free-text comments on releases with emoji reactions (`🔥🫀🌙🐘`) — **no star ratings, and none planned** (explicit product decision: reputation is earned through what you write, not a score). Users can edit their own comment (silent overwrite, marked "· edited," no history kept) from the release page (live Firestore subscription, `subscribeToReleaseComments`). The "Your Reviews" list (`subscribeToCommentsByUser`) lived on the Me tab, which is cut, so it's currently unreachable.
- **Release detail**: square cover art (`aspectRatio: 1`; all sources serve 1:1), tags, label, blurb, optional sample-play button (`sampleUrl` + `sampleTrackTitle`), streaming links, and three highlight blocks — `editorsTake` (rose), `criticsHighlight` (amber, manually curated, no scraping pipeline), `userHighlight` (olive, a hand-copied standout comment). A header bookmark toggles a personal save (`savedReleases` collection, doc id `${uid}_${releaseId}`). There is no screen yet that lists saved releases.
- **Firestore rules + indexes**: deployed and current (`firestore.rules`, `firestore.indexes.json`). Comment edits are restricted server-side to the comment's own author and only the `text`/`editedAt` fields.

## Toolchain setup on a new/returning Mac

1. **Xcode**: already handled per the user on this pass — confirm `xcodebuild -version` matches what the installed Simulator runtimes support.
2. **Node**: use `nvm` (not a system/Homebrew Node). If `nvm` isn't installed: `curl -o- https://raw.githubusercontent.com/nvm-sh/nvm/v0.40.1/install.sh | bash`, then `nvm install --lts` and `nvm use --lts`.
3. **CocoaPods**: try `gem install cocoapods` on system Ruby first. If that fails (old system Ruby, e.g. 2.6) **and** Homebrew won't install either (Homebrew 7.0.0+ dropped Intel support — check with `brew --version` / `arch`), the fallback that worked on the other Intel Mac this session was:
   - Install `rbenv` + `ruby-build` (via a manual git clone into `~/.rbenv` if Homebrew is unavailable, per rbenv's own README).
   - Build a modern Ruby from source: `rbenv install 3.3.6` (may need `libyaml` built manually first for the `psych` extension — see rbenv/ruby-build troubleshooting if this errors).
   - `rbenv global 3.3.6`, then `gem install cocoapods` on that Ruby.
   - Skip all of this entirely if the Air is Apple Silicon — Homebrew works fine there, just `brew install cocoapods` (or `brew install rbenv ruby-build` if you still prefer rbenv).
4. **EAS CLI**: `npm install -g eas-cli` (or `npx eas-cli`), then `eas login` (existing account/project credentials are stored server-side on Expo's servers — no local credential files needed for building or submitting).
5. **Firebase CLI** (only needed if deploying rules/indexes or running the publish script from this machine): `npm install -g firebase-tools`, then `firebase login`.
6. **`GoogleService-Info.plist`**: already committed to the repo (contains only a public client API key, no secrets) — nothing to manually place.
7. **`service-account.json`**: gitignored, NOT in the repo. Only needed to run `scripts/publish-releases.ts` locally. Download fresh from Firebase Console → Project Settings → Service Accounts → Generate new private key, drop it at the repo root. Never commit it.
8. **Install deps**: `npm install`, then `cd ios && pod install` (or just let `npx expo run:ios` do it).

## Building

- **Local Simulator/device run**: `npx expo run:ios` (add `--device "iPhone 17 Pro"` or similar to target a specific Simulator). Remember: phone auth won't complete in Simulator once App Check enforcement is on — real-device only for that flow.
- **TestFlight build**: `npx eas-cli build --platform ios --profile production --non-interactive --auto-submit` (profile + `ascAppId` already configured in `eas.json`).
- **Weekly release publish**: `npm run publish-releases` (wraps `scripts/publish.sh`) — first point `scripts/data/current.ts` at that week's `scripts/data/releases-<date>.ts` (the one pointer shared by the publish script and the QA preview). Content changes reach the app immediately; no build or OTA update needed. Do not run `npx ts-node scripts/publish-releases.ts` directly — see gotcha below.
- **Best-of list**: lives in the `releases` collection as docs with a `bestOf: { year, rank, metacriticScore }` field (their `weekOf` is the real release Friday, so the latest-week Browse query never treats them as "this week"). Edit `scripts/data/best-of-<year>.ts` and run `npm run publish-best-of` (`scripts/publish.sh publish-best-of`) — no build or OTA needed. Tapping a row opens the normal release detail (cover, links, save, comments). Cover art and Apple Music links came from the iTunes Search API; entries it couldn't find have no cover/links and need manual verification (currently Madonna — Confessions II and Iceage — For Love of Grace & the Hereafter).
- **Preview a draft week (editor QA)**: `EXPO_PUBLIC_QA_MODE=1 npx expo start`, then open the app in the Simulator. It swaps the app root for `src/qa/ReleaseQAScreen.tsx`: no sign-in, lists the week in `scripts/data/current.ts` with a per-release checklist of which optional fields are filled, and tapping one opens the real `ReleaseDetailScreen`. Nothing is published.
- **Ship a JS-only fix (OTA)**: `npx eas-cli update --branch production --message "..." --environment production --non-interactive` (`--environment` is required in non-interactive mode). Runtime version policy is `appVersion`, so updates only reach builds of the same `version` that include `expo-updates` (TestFlight build #8 and later; build #7 never receives OTA). **Committing/pushing does not ship anything to phones** — a JS change isn't live until you run this (or ship a new build). Native changes (new native modules, Info.plist, Podfile, plugins) still need a full build.

## Known gotchas from this session, so they're not re-debugged from scratch

- **The marketing site (`corners.thefanlab.com`, repo `jmaples42/corners`) is a static May 2026 mock** — plain HTML, hardcoded sample data, no Firestore code. It does not update when releases are published. `firestore.rules` already allows public read on `releases` for this purpose; the client-side fetch was never written. Deferred on purpose ("core product first").

- If `npx tsc --noEmit` shows `error TS2305: Module '"firebase/auth"' has no exported member 'getReactNativePersistence'` — this is a known, harmless false-positive (plain `tsc` resolves the web build of `firebase/auth`, not the React-Native-specific export Metro picks correctly at runtime). Ignore it.
- **`npx ts-node scripts/publish-releases.ts` silently does nothing on Node v23+** (exit 0, zero output, nothing published to Firestore) — Node's own native TypeScript loader (`--strip-types`, on by default since Node 23) intercepts `.ts` files before ts-node 10.9.2's require hook can register, so ts-node never actually runs the script. Confirmed on Node v24.21.0. Use `npm run publish-releases` instead (`scripts/publish.sh`), which sidesteps this by compiling to plain JS with `tsc` first and running that with `node`. If ts-node itself ever gets updated to support this natively, this workaround can be retired — check by running `npx ts-node scripts/publish-releases.ts` and confirming it actually logs `Publishing N releases...` before reverting to the direct command.
- If real SMS silently doesn't arrive (request accepted, no error, no text): check, in order — Blaze billing is active on the **Firebase Console** billing indicator specifically (bottom-left of any Firebase Console page), not just linked in Google Cloud Console; SMS region policy (Authentication → Settings → SMS region policy) includes the destination country; the number isn't sitting in Authentication → Sign-in method → Phone → "Phone numbers for testing" (a stale test-number entry silently short-circuits real SMS forever for that number). If all of that checks out and it's still silent, it may be a per-number anti-abuse flag on Google's side — Firebase Support is the only way to get visibility into that, since Google deliberately doesn't expose delivery-block reasons in any console.
- **Xcode 27 / iOS 27 Simulator: app crashes instantly on launch (`SIGTRAP` in `UIApplicationEvaluateRuntimeIssueForNoSceneLifecycleAdoption`)**. iOS 27 hard-crashes apps that never adopt the UIScene lifecycle — previously this was just a soft warning. This app's AppDelegate-only, single-window template (no SceneDelegate) trips it on every launch; a debugger attached via Xcode's own Run button can mask this (its exception handling behaves differently from a plain `simctl launch`), which is why it may not show up if you're used to running from Xcode. Fixed via two committed Expo config plugins — `plugins/withSceneDelegate.js` (adds a real `SceneDelegate.swift` + `UIApplicationSceneManifest`, moves window/`startReactNative` creation out of `AppDelegate.didFinishLaunchingWithOptions` into the scene delegate) and `plugins/withPodfileDeploymentTargetFix.js` (a few pods' auto-generated privacy-manifest targets default to deployment targets below Xcode 27's new 15.0 minimum and fail to build otherwise) — both registered in `app.json`'s `plugins` array, so they reapply automatically on every `expo prebuild`. If this ever needs re-diagnosing: build/launch succeeding but the app disappearing back to the home screen instantly means check `~/Library/Logs/DiagnosticReports/Corners-*.ips` for the crash signature before assuming it's a JS-side issue.
